# 中文物流语音客服：问题、方案与工程复盘

> 用途：简历项目描述、技术面试项目复盘、系统设计讨论。
> 最后核对：2026-11-15（北京时间）。
> 事实口径：本文严格区分“已实现”“已自动验证”“已真人验证”和“待验证”，不把计划写成成果。

## 1. 项目概述

这是一个基于 LiveKit Agents 的中文物流语音客服。系统连接本地 Fleetbase 后端，支持：

- 查询运单状态；
- 查询可用派送时段；
- 在用户明确确认后提交改约；
- 通过语音或 LiveKit 原生文本消息输入运单号；
- 在 STT、TTS 或上游 API 出现异常时失败安全，不猜测运单号，不误查、不误改。

项目并不是“给大模型几个工具就完成”。真正困难的是把概率性的语音识别和语言模型，约束在确定性的业务状态机、安全边界和后端一致性检查中。

当前默认链路为：

```text
麦克风
  -> AssemblyAI Universal-3.6 Pro 中文 STT
  -> LiveKit AgentSession / Gemma 4 31B
  -> 确定性工具与会话状态机
  -> Fleetbase API
  -> Fish Audio S2.1 Pro 中文男声 TTS
  -> 耳机或扬声器
```

## 2. 可以写进简历的项目摘要

以下内容可按岗位方向选用，不建议全部堆进一条简历描述。

### 2.1 综合版

基于 LiveKit Agents、Python 与 Fleetbase 构建中文物流语音客服，实现运单精确查询、派送时段查询及跨回合确认改约；通过确定性状态机、精确匹配、乐观并发检查和幂等回读约束 LLM 工具调用，修复 STT 错号导致上游返回无关订单的高风险漏洞。针对中文长数字串完成 AssemblyAI/Deepgram STT 与 Cartesia/Fish Audio TTS A/B、provider-aware 回合检测，并对纯数字流程和明确打断做部分真人麦克风验收；本地回归测试达到 47/47 通过，并保留文本、音频模拟和只读后端 smoke 多层验证。

### 2.3 偏语音 AI

为中文物流场景设计可回滚的 STT/TTS provider profile：对 AssemblyAI Universal-3.6 Pro 使用其原生 EOT，避免叠加 LiveKit endpointing 延迟；Deepgram 回滚路径保留 LiveKit Turn Detector。通过合成样本、LiveKit audio simulation 和真人麦克风定位长数字串分段、late transcript、TTS 缓冲不足及蓝牙通话模式问题，并以精确匹配、逐位复述确认和文本输入兜底保证失败安全。

## 3. 系统设计原则

### 3.1 概率模型负责理解，确定性代码负责状态和副作用

LLM 可以判断用户意图、选择工具和组织自然语言，但不能单独决定：

- 哪个运单号是真实目标；
- 本轮是否已经得到确认；
- 是否允许写数据库；
- 上游返回的订单是否真的匹配请求；
- 并发修改后是否仍能提交；
- API 超时后是否已经成功写入。

这些判断全部落到 Python 状态与后端客户端中。工具描述只是第一层提示，代码中的前置条件才是安全边界。

### 3.2 失败安全优先于“尽量猜对”

物流运单号属于高风险标识符。项目明确拒绝模糊匹配：

- STT 少一个字符：拒绝查询或返回未找到；
- 上游忽略过滤条件：客户端再次精确匹配；
- 用户尚未确认：不查询或不提交；
- 订单版本变化：拒绝提交；
- 结果不确定：提示复述或改用文本输入。

目标不是让每次语音都成功，而是让失败不会变成错误业务操作。

### 3.3 读操作和写操作采用不同风险等级

查询可以在确认运单号后执行；改约属于外部写入，采用更严格的两阶段流程：

```text
用户选择时段
  -> prepare_reschedule：只生成提案，不写入
  -> 客服复述目标和时间
  -> 后续独立用户回合明确确认
  -> commit_reschedule：重新检查订单，再提交
  -> 回读确认最终状态
```

同一用户消息中即使 LLM 连续调用准备和提交，状态机也会拒绝提交。

## 4. 关键问题一：上游列表接口导致错误运单命中

### 4.1 现象

音频模拟中，用户说的是合成运单 `DEMO1234`，STT 将其识别为 `DM01234`。Fleetbase 的 `/v1/orders` 接口在该运行环境中返回了未按 tracking number 过滤的列表，旧客户端直接取列表第一条，导致错误号码命中了另一张测试订单。

这是项目中风险最高的问题：它把普通的 STT 错字放大成了跨订单数据错误。

### 4.2 根因

根因不是单独某个模型不准，而是多层系统同时做了过度信任：

1. 客户端假设上游一定执行查询参数过滤；
2. 客户端假设列表第一项就是目标订单；
3. 客户端没有对响应中的 tracking number 做二次核对；
4. 语音输入天然可能出现字符替换、漏字或分段。

### 4.3 解决方案

在 `FleetbaseClient.lookup_waybill` 中建立确定性匹配：

1. 规范化请求运单号；
2. 长度不足直接返回未找到，不访问危险路径；
3. 调用 Fleetbase 查询接口；
4. 无论响应是单对象还是列表，都提取每个订单的 tracking number；
5. 对响应 tracking number 使用相同规范化规则；
6. 只接受与请求完全相等的订单；
7. 找不到精确项时返回 `found: false`，绝不取“最像”或第一项。

### 4.4 为什么不用模糊匹配

编辑距离、拼音相似度或前缀匹配在搜索推荐中可能有用，但不适合直接授权物流查询或改约。一个字符的差异可能代表完全不同的客户订单。正确策略是：

- 语音层可以帮助用户复述；
- 展示层可以建议改用键盘；
- 业务执行层只能精确匹配。

### 4.5 验证

- 新增回归测试，模拟上游返回不相关列表项，断言错误号码返回 `found: false`；
- 使用真实本地 Fleetbase 只读查询验证 `DM01234` 不会命中；
- 后续音频模拟即使出现号码分段，也没有误命中或误提交。

### 4.6 面试讲法

重点不是“我加了一个 if”，而是：

> 我发现语音识别错误本身不可避免，真正的安全漏洞是后端客户端把上游过滤当成可信边界。我把过滤后置校验放到自己控制的代码里，使任意 STT 错误最多退化为查询失败，不能演化成跨订单访问。

## 5. 关键问题二：LLM 可能在同一回合完成高风险写入

### 5.1 现象

如果只依赖提示词“请在用户确认后提交”，LLM 仍可能在一个用户消息中先调用准备工具，再立即调用提交工具。语言模型看到用户说“帮我改到明天下午”时，可能把选择和确认合并理解。

### 5.2 根因

- 提示词不是事务约束；
- 工具调用顺序正确，不等于业务授权正确；
- 模型可能把同一句话中的意愿当成最终确认；
- 失败重试可能导致重复写入。

### 5.3 解决方案：跨回合状态机

会话状态 `LogisticsSessionState` 保存改约提案，提案至少绑定：

- 运单号；
- 目标派送时间；
- 准备阶段对应的用户消息 ID；
- 准备时读取到的订单版本信息；
- 提案 ID。

提交工具必须满足：

1. 提案存在且未失效；
2. 当前用户消息 ID 与准备阶段不同；
3. 用户在后续回合明确确认；
4. 提交前重新查询订单；
5. 当前订单版本与准备阶段一致；
6. API 写入后回读最终状态。

### 5.4 并发修改与乐观检查

准备和提交之间，订单可能被其他客服或系统修改。项目在提交前重新读取订单并比较 `updated_at` 等状态：

- 未变化：允许提交；
- 已变化：抛出冲突，要求重新查询和确认；
- 已经是目标时间：识别为幂等重放，而不是重复失败。

### 5.5 不可打断区

在真正执行 `commit_reschedule` 时调用 `context.disallow_interruptions()`，避免正在进行外部写入时因用户语音打断造成前端听感与后端状态不一致。这里的“不允许打断”只包裹短暂提交阶段，不应扩展到整段普通客服回答。

### 5.6 验证

- 准备阶段不写入；
- 同一用户消息提交被拒绝；
- 后续确认只提交一次；
- 订单并发变化阻止提交；
- 用户说“先不要提交”后只生成提案；
- 随后取消时没有调用提交工具；
- 关闭会话后直接回读 Fleetbase，`scheduled_at` 和 `updated_at` 均未变化。

### 5.7 面试讲法

> 我没有把确认逻辑留在 prompt 中，而是把“不同用户消息”作为状态机可验证条件，并在提交前做乐观并发检查。LLM 负责理解确认语义，代码负责判断这次确认是否有资格产生副作用。

## 6. 关键问题三：运单查询本身也需要复述确认

### 6.1 现象

即使查询是只读操作，错误运单号也可能暴露其他订单信息，并污染后续改约上下文。早期流程在同一回合拿到号码后直接查询，用户没有机会确认 STT 是否听对。

### 6.2 解决方案

查询流程也改成两轮：

```text
第一轮：用户口述号码
  -> 规范化
  -> 保存 WaybillCandidate
  -> 逐字符复述
  -> 禁止在本轮 lookup

第二轮：用户确认
  -> 验证候选存在
  -> 验证用户消息 ID 不同
  -> 验证查询号码与候选完全相同
  -> 执行精确查询
```

如果用户纠正号码，则覆盖旧候选并重新复述；不能把纠正语句直接当作确认。只有精确查询成功的运单号，才能授权后续时段查询。

### 6.3 为什么保存用户消息 ID

单纯的布尔值 `confirmed=True` 无法证明确认发生在后续回合。绑定消息 ID 可以阻止模型在一个用户消息内连续调用 `prepare_waybill_lookup` 和 `lookup_waybill`。

### 6.4 验证

- 没有准备候选时拒绝查询；
- 同一消息内拒绝查询；
- 不同号码拒绝确认；
- 用户纠正时覆盖候选；
- 放弃候选后必须重新复述；
- 未成功查询的号码不能查询派送时段；
- 真人说“一二三四五六七八”后先逐位复述，后续“正确”才查询成功。

## 7. 关键问题四：中文口述数字与系统运单号格式不一致

### 7.1 现象

真人语音中，STT 正确输出“一二三四五六七八”，但后端把中文字符串原样作为 tracking number 查询，因此返回未找到。问题不在识别准确率，而在识别结果与业务标识格式不一致。

### 7.2 解决方案

在统一的 `normalize_waybill` 中执行：

- Unicode NFKC 归一化，处理全角字母和数字；
- 去除业务允许忽略的空格与分隔符；
- 统一字母大小写；
- 当候选为纯数字或 ASCII 字母数字标识时，将其中的 `零/〇/○/幺/一...九` 确定性映射为 ASCII 数字；
- 遇到 `十/百/千/万` 等带计数语义的写法不做猜测；
- 仍拒绝无字母的中西数字混写，以避免把自然数表达式误当作逐字符标识。

### 7.3 安全取舍

“一二三四”可以无歧义地逐位映射为 `1234`；“一百二十三”可能表示 `123`，也可能是口述字符的一部分，不能用简单替换。项目选择只转换无歧义子集。

### 7.4 混合字母数字缺口与修复边界

真人复测曾得到 `log九一一三一八零四三八sg`，早期规则只转换纯中文数字串，因此候选无法匹配 ASCII 运单号。提交 `aad489b` 将规范化改为受限的逐字符映射：只有候选包含 ASCII 字母且其余字符均为 ASCII/中文逐位数字时才转换，使该输入确定性得到 `LOG9113180438SG`。

该修复已通过规范化单测、状态机回归、后端精确查询回归和文本 debugger；仍未把自动化证据升级为真人麦克风证据。`十/百/千/万`、无字母的中西数字混写和模糊近似号码继续安全失败。

### 7.5 面试讲法

> 我把“STT 输出正确”与“业务标识可用”分开看。通过 Unicode 归一化和受限字符映射解决格式鸿沟，但刻意不实现中文数词解析器，因为在订单标识场景中，少做猜测比多做智能转换更安全。

## 8. 关键问题五：中文长数字串的 STT 准确率和分段

### 8.1 现象

长数字和字母数字混合串对语音识别很难：

- 数字可能被转成中文、ASCII 或相似发音；
- 字母可能被替换；
- 用户在分组之间自然停顿；
- STT 可能提前发出 end-of-turn；
- 合成语音与真人麦克风的停顿分布不同。

### 8.2 A/B 方法

项目没有只凭主观印象选模型，而是保留可通过环境变量切换的 provider profile：

- AssemblyAI Universal-3.6 Pro：默认 accuracy profile；
- Deepgram Nova-3：回滚和 A/B；
- `baseline` profile：回到 provider 默认参数；
- `auto:zh`：交给 LiveKit 选择中文 provider。

测试维度包括：

- 同一组固定话术；
- 完整转写次数；
- 是否被拆成多个回合；
- transcript delay；
- 是否出现 late transcript；
- 最终工具参数是否正确；
- 即使错误时是否仍失败安全。

### 8.3 当前结论

小样本合成 8 位运单号中，AssemblyAI 完整转写 3/3，Deepgram 为 2/3，因此默认切回 AssemblyAI。这个样本量不足以证明普遍优势，Deepgram 配置仍保留为回滚路径。

### 8.4 关键词和提示

accuracy profile 添加了物流场景 prompt 和统一 keyterms，覆盖运单号、包裹状态、派送时段、改约、英文字母和数字等领域词。风险是当前 keyterms 中含有合成夹具号码，可能对演示订单产生偏置；移除前需要做同组 A/B。

### 8.5 文本输入兜底

项目复用 LiveKit 原生 `lk.chat`，没有自建另一套文本传输协议。语音可以无限重试，键盘输入始终是可选项，而不是惩罚式地等多次失败后才出现。生产界面仍应为长运单号提供文本或按键输入。

## 9. 关键问题六：回合检测重复等待导致延迟

### 9.1 现象

AssemblyAI Universal-3.6 Pro 已经提供自己的 end-of-turn，但早期配置仍叠加 LiveKit Turn Detector 和 endpointing 等待。日志出现 EOT probability、动态等待和 late transcript，回复延迟偏高。

### 9.2 根因

把所有 STT provider 当成相同能力：

- AssemblyAI 有原生 STT EOT；
- Deepgram Nova-3 回滚路径依赖 LiveKit Turn Detector；
- 如果两层都决定“用户是否说完”，等待时间可能叠加。

### 9.3 解决方案：provider-aware turn handling

- AssemblyAI：`turn_detection="stt"`，`endpointing.min_delay=0`，让 provider 的 EOT 直接提交；
- Deepgram 和其他回滚 provider：保留 `inference.TurnDetector()`；
- 用单一 helper 生成配置，并用单元测试固定 provider 到模式的映射；
- provider 专属参数只发送给对应 provider，避免网关收到未知参数。

### 9.4 验证

同组三次带停顿的合成 8 位号码，修改前后均为 3/3 完整；修改后日志均显示 `source: stt`，不再出现旧的 EOT probability/2.5 秒动态等待或 late-transcript warning。观测端到端延迟从约 3.05–4.50 秒降到约 2.03–2.62 秒。

### 9.5 尚未解决的问题

当前 `min_turn_silence=500 ms`、`max_turn_silence=1500 ms` 是业务候选值，不是普适最优值。合成音频的异常长停顿曾超过 1500 ms，导致号码被拆分；真人也报告客服有时过早接话。是否提高上限必须用同一真人麦克风做 A/B，不能只根据异常合成样本直接增加所有普通回合的等待。

## 10. 关键问题七：客服抢话与不自然打断

### 10.1 两个不同问题

用户体验中的“打断”实际包含两个方向：

1. 用户还没说完，系统提前结束用户回合并开始回答；
2. 客服正在说话时，用户想插话，但系统没有自然地让出话权，或把“嗯、好”误判成真插话。

第一个由 STT EOT 和 endpointing 控制；第二个由 interruption handling 控制。它们不能靠一个阈值同时解决。

### 10.2 实现方案

LiveKit 最新文档和本地 `livekit-agents==1.8.10` 源码都支持 adaptive interruption。项目不再依赖 production mode 下的默认行为，而是显式配置 `mode="adaptive"`、`min_duration=0.5`、`min_words=0`、`resume_false_interruption=True`、`false_interruption_timeout=2.0` 和 `backchannel_boundary=(1.0, 1.0)`。这套配置与 STT EOT 分离：前者只决定客服说话时是否让出话权，后者仍决定用户何时说完。

### 10.3 验证与证据边界

- 单元测试固定自适应打断和 provider-aware 回合检测的组合；包含后续混合运单修复在内的最新本地回归为 47/47 通过；
- 2026-11-13 真人 Console 中 detector 初始化并创建 session，没有回退为普通 VAD；用户在客服回复中说“你别说了”，检测器在约 0.55 秒处以约 0.86 概率判为真实打断，界面将回复标记为 `interrupted`；
- 2026-11-15 另一轮真人 Console 中 detector 同样完成初始化，但随后发生 0.8 秒推理超时（HTTP 408）；SDK 禁用 adaptive detector 并回退到普通 VAD，之后附和词“哎”打断了运单号复述；
- 两轮证据共同说明“明确打断可生效”，也暴露 detector 服务不可用时 backchannel 区分能力会消失。不能据此声称“嗯/好”不误打断；背景噪声与误打断续播仍待受控 A/B；
- AssemblyAI `max_turn_silence` 未在本阶段修改，耐心倾听的用户端停顿问题仍需单独测试。

不能简单关闭所有打断，因为真实客服必须允许用户说“停”“不对”“不要提交”。也不能只把 VAD 灵敏度调低，因为那会让真正的紧急纠正更难生效。

## 11. 关键问题八：TTS 卡顿、电音和模型选择

### 11.1 现象分层

听起来都像“声音有问题”，实际至少有三类：

- TTS provider 生成慢或流式供给不足；
- 网络或 LiveKit Inference 连接重试；
- Windows 蓝牙耳机切入 Hands-Free 通话模式导致音质下降。

### 11.2 设备链路隔离

通过 `lk agent console` 枚举并显式选择音频设备，对比：

- 电脑麦克风阵列；
- 外部 Realtek 麦克风；
- Realtek 有线耳机；
- WH-1000XM4 立体声输出与 Hands-Free 输入。

有线耳机播放正常，而问题集中在蓝牙通话路由，说明“电音”不能直接归因于 Cartesia 输出。

### 11.3 TTS A/B

项目保留多条可回滚路径：

- 默认 Fish Audio S2.1 Pro 中文男声；
- Cartesia Sonic 3 / 3.5 / 3.6 环境变量 A/B。

2026-11-12 的早期对照中，Sonic 3.5 曾连续两轮生成完整中文并回到 listening，TTFB 约 0.43–1.02 秒，而 Sonic 3 一次超过 30 秒仍停在 speaking。2026-11-13 在相同麦克风、耳机和网络下重新真人 A/B：Sonic 3.5 约 40 秒内反复触发慢音频 flush，Sonic 3.6 仍明显断续；Fish Audio 男声能完成问候和回复，用户连续两次确认“很顺”，仅后续偶发一次 flush。因此当前默认切回 Fish。该结论是单次同场运维证据，不外推为通用供应商性能结论。

### 11.4 正确理解 `flush audio emitter`

通过查看 LiveKit 源码确认，`flush audio emitter due to slow audio generation` 是在生成跟不上播放时释放缓冲、避免持续饥饿的 DEBUG 保护行为，不等同于 API 请求失败。验收必须综合：

- 最终 assistant item 是否完整；
- 状态是否回到 listening；
- 下一轮是否正常；
- 真人听感是否断续；
- 是否同时出现 provider error 或连接重试。

### 11.5 最新卡顿证据

早期真人 Console 中首先出现一次 LiveKit Inference LLM `ConnectError` 并自动重试，随后同一回复连续出现多次 audio emitter flush；另有 105–120 ms 的本地事件循环短阻塞。2026-11-15 的另一轮实测没有把单条 flush 当作失败，但同一会话多次出现该日志，并能主观感到回复延迟；回复最终仍可完成。两轮证据更支持云端连接或 TTS 流供给不足是主要嫌疑，本地短阻塞是次要因素，仍需用固定短话术记录 TTFB、flush 次数和完整性。

## 12. 关键问题九：本地 Fleetbase 与 Docker 运行环境恢复

### 12.1 Docker Desktop Secrets Engine 故障

Docker Desktop 无法正常启动。检查后确认不是 WSL 2 或硬件虚拟化未开启，而是旧的 `docker-secrets-engine/engine.sock` reparse-point 导致 Secrets Engine 无法处理。单文件移动和删除都被系统拒绝。

处理方式：

1. 确认 Docker 进程停止；
2. 关闭 WSL；
3. 将整个 secrets engine 目录隔离为带时间戳的备份；
4. 创建新的空目录；
5. 重启 Docker Desktop；
6. 验证 Docker server 和 Compose 服务。

这个操作选择“隔离备份”而不是直接删除，保证可恢复性。

### 12.2 Scheduler 健康检查误报

Fleetbase scheduler 被标记 unhealthy，但定时任务实际可能正常。根因是本地 override 健康检查调用镜像中不存在的 `ps`。改为读取 `/proc/1/comm` 检查 `go-crond` 后，容器达到 healthy，定时任务每分钟 exit code 0。

### 12.3 验证

- Docker server 29.9.2 可响应；
- Fleetbase 8 个 Compose 服务运行；
- 带健康检查的服务均 healthy；
- 默认只读 smoke 返回 `lookup_found: true` 和 3 个派送时段；
- smoke 默认不写入，只有显式 `--commit` 才允许提交。

## 13. 关键问题十：云端凭据、部署状态与网络边界

### 13.1 凭据过期

原 LiveKit 项目凭据开始对 Inference LLM/STT 返回 401。通过官方 `lk cloud auth` 重新授权，再使用 `lk app env --write` 写入 Git 忽略的 `.env.local`。旧文件只做本地备份，不输出、不提交。

验证方式不是“命令成功”，而是无 `--project` 参数启动普通 debugger，实际完成一轮音频请求。

### 13.2 开发 worker 不等于 Cloud 部署

早期记录中的 `dev-*` 只表示开发 worker 连接。重新核对 Cloud 控制台和 `lk agent status` 后确认：

- 控制台显示 Self-hosted / Not deployed yet；
- CLI 返回 no agents found；
- 仓库没有 `livekit.toml`。

因此不能把本地 dev 连接描述成“已部署生产 Agent”。

### 13.3 localhost 的云端不可达性

Fleetbase 目前位于本机 `localhost:8000`。即使立即部署 LiveKit Cloud Agent，云容器也不能访问用户电脑的 localhost。首次公开演示前必须单独解决：

- Fleetbase 云端部署或安全隧道；
- 网络访问控制；
- 凭据和密钥管理；
- Agent Embed 的文本聊天设置；
- 公开环境的数据隔离。

用于验证工具选择和状态机，不经过 STT/TTS，定位更快。适合确认：

- Fleetbase 精确查询成功；
- 查询时段和“先不要提交/取消”不会写入。

## 15. 可复现与可回滚设计

### 15.1 环境变量而不是改代码切模型

STT、TTS、profile、voice 和 expressive 行为均保留环境变量开关。A/B 不需要反复改源码，降低比较过程引入其他变量的风险。

### 15.2 幂等合成夹具

`ensure_audio_fixture.ps1` 创建独立合成订单，并只在 localhost Fleetbase 中把号码固定为 `12345678`。重复执行返回 already exists，避免每轮测试创建重复数据。

### 15.3 smoke 默认只读

`smoke_fleetbase.py` 默认只做查询和时段读取；只有显式传入 `--commit` 才执行真实改约。把“安全默认值”放进工具接口，而不是依赖操作者记忆。

## 16. 方案取舍与被拒绝的做法

### 16.1 拒绝模糊运单匹配

原因：召回率提升不值得跨订单误命中风险。采用精确匹配、复述确认和文本兜底。

### 16.2 拒绝只靠 prompt 控制写入

原因：prompt 不能提供事务保证。采用会话状态、消息 ID、版本检查和回读。

### 16.3 拒绝为文本兜底自建协议

原因：LiveKit 已原生支持 `lk.chat`。复用官方路径减少客户端、鉴权和消息同步成本。

### 16.4 拒绝根据一次合成失败直接提高全局停顿阈值

原因：异常合成音频停顿与真人不同，提高全局阈值会让所有正常回合变慢。先做真人同设备 A/B。

### 16.5 拒绝把任何一次 `flush audio emitter` 当成 TTS 故障

原因：它是保护性 DEBUG 行为。必须结合最终消息、状态、连接错误和真人听感。

### 16.6 拒绝把 dev worker 描述为云端部署

原因：开发连接、Cloud Agent 和公开 Embed 是不同运行状态。以控制台、CLI 和部署配置三方证据为准。

## 18. 面试问题与参考回答

### 18.1 为什么不用大模型直接处理所有逻辑？

大模型适合处理自然语言的不确定性，但订单标识、授权和写入必须可重复验证。项目让模型负责意图，代码负责状态和副作用。即使模型工具调用错误，状态机和精确匹配仍会拒绝危险操作。

### 18.2 项目中最严重的 bug 是什么？

STT 把运单号识别错后，上游列表接口没有可靠过滤，旧客户端又取第一项，导致错号命中其他订单。修复不是换一个更准的 STT，而是在客户端对响应 tracking number 做规范化后的精确匹配，把语音错误限制为安全失败。

### 18.3 如何保证用户真的确认了改约？

准备和提交绑定不同的用户消息 ID。准备阶段保存提案和订单版本，不写入；只有后续独立消息明确确认，且订单未被并发修改，才能提交。提交后再回读，识别幂等成功或冲突。

### 18.4 如何评估 STT 模型？

固定话术和设备，比较完整转写、分段、延迟、late transcript、工具参数及失败安全，而不是只看一条文字是否“差不多”。合成测试适合重复比较，真人麦克风负责最终验收。

### 18.5 为什么 AssemblyAI 用 STT EOT，而 Deepgram 用 LiveKit Turn Detector？

因为 provider 能力不同。AssemblyAI Universal-3.6 Pro 已提供自己的回合结束信号，再叠加 detector 会增加等待；Deepgram Nova-3 回滚路径没有使用同样的 EOT 配置，所以保留 LiveKit Turn Detector。配置按 provider 选择，并有单元测试固定映射。

### 18.6 怎么处理用户打断？

先区分“用户是否说完”和“客服说话时用户是否真想插话”。前者由 STT EOT/endpointing 决定，后者显式使用 adaptive interruption 区分真实 barge-in 与“嗯、好”或噪声，并保留误打断续播。当前已验证 detector 可用时“你别说了”会真实打断；也实测到 detector 推理超时后 SDK 回退普通 VAD，此时“哎”会误打断复述。“嗯/好”、噪声和续播仍需在 detector 可用与回退两种状态下分别 A/B。

### 18.7 如何证明没有误写数据库？

除了检查工具调用，还要关闭会话后直接回读 Fleetbase。项目在“先不要提交—取消”的测试中确认 `scheduled_at` 和 `updated_at` 未变化。smoke 默认也设计为只读，写入必须显式 `--commit`。

### 18.8 如果 API 超时但实际上已经写入怎么办？

不能简单重试写操作。提交后回读当前订单；如果目标状态已经存在，则按幂等重放处理，否则报告不确定或冲突，避免重复提交。

### 18.9 你如何区分代码完成和功能完成？

项目采用分层证据：单元测试证明确定性逻辑，debugger 证明工具序列，simulation 证明整段行为，后端 smoke 证明集成，真人 Console 证明真实语音和设备体验。没有真人或真实后端证据的内容明确标记为待验证。

## 19. STAR 讲述模板

### 情境（Situation）

我在做中文物流语音客服时发现，语音识别错误不仅影响体验，还可能通过工具调用放大成查错订单或误改约；同时长数字串会被分段，回合检测和 TTS 也存在延迟与卡顿。

### 任务（Task）

目标是在不依赖“模型永远识别正确”的前提下，实现可用且失败安全的运单查询和改约，并建立能区分逻辑、模型、网络和设备问题的验证体系。

### 行动（Action）

我把模型和业务状态解耦：对上游响应做运单号精确复核；为查询和改约分别建立跨回合确认状态机；提交前重新读取订单做并发检查；根据 STT provider 选择不同回合检测；保留多模型环境变量 A/B；使用单元测试、LiveKit debugger/simulation、后端 smoke 和真人麦克风逐层验证。

### 结果（Result）

修复了错号命中其他订单的高风险漏洞；纯数字运单已真人验证“识别—复述—确认—精确查询”，并验证 STT 把短确认误转时 Agent 会澄清而不查询；混合字母中文数字已自动化和文本 debugger 验证；取消改约后直接回读确认无写入；最近行为代码达到 47/47 测试通过。provider-aware 回合检测在小样本中将端到端延迟从约 3.05–4.50 秒降至 2.03–2.62 秒。自适应打断已显式启用，并真人验证“你别说了”会终止客服回复；另一轮也暴露 detector 超时回退 VAD 后附和词会误打断。混合运单真人转写、backchannel、背景噪声与 TTS 稳定性仍明确保留为待验收项。
